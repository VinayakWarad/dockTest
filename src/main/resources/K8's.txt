Diff between PV and PVC ?
PVC :
Persistent Volume Claim (PVC) - >Request for storage-> Application says:"I need 1Gi storage"->Kubernetes finds/binds matching PV.
Pod-> PVC  (request) -> PV   (actual storage)->Physical Disk

Example PVC : Give me 1Gi persistent storage
apiVersion: v1
kind: PersistentVolumeClaim
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
	  
Example PV : Actual 10Gi storage exists	  
apiVersion: v1
kind: PersistentVolume
spec:
  capacity:
    storage: 10Gi
	
| PVC                 | PV                       |
| ------------------- | ------------------------ |
| requested by app    | actual storage           |
| logical abstraction | physical/storage backend |
| app-facing          | infrastructure-facing    |

Note : In Modern Kubernetes -> you create ONLY PVC ->Kubernetes dynamically creates PV automatically using: ->StorageClass ->This is what happened in your PostgreSQL Helm install.	

Real Production Example :PostgreSQL Pod says:I need 8Gi persistent storage -> PVC created. ->Cloud provider dynamically provisions->EBS disk,Azure Disk,GCP Persistent Disk as PV.
NEVER directly care about PV :Apps request storage via:PVC ->Infrastructure handles:PV provisioning.

Understand WHY StatefulSet Exists
 Deployment works great for:, stateless apps, APIs, Spring Boot services BUT databases need: stable storage, stable hostname, stable Pod identity That’s why: StatefulSet exists
 | Deployment           | StatefulSet      |
| -------------------- | ---------------- |
| random pod names     | stable pod names |
| interchangeable pods | unique identity  |
| stateless            | stateful         |
| shared behavior      | ordered behavior |

StatefulSet Guarantees
 1. Stable Pod Names, Example:, my-postgres-postgresql-0, my-postgres-postgresql-1, my-postgres-postgresql-2, These NEVER randomly change.
 2. Stable Network Identity, Each pod gets stable DNS, Example: my-postgres-postgresql-0.my-postgres-postgresql-headless, Used in:, PostgreSQL replication, Kafka, Elasticsearch, MongoDB
 3. Stable Storage, Each replica gets:, its own PVC, Example:, data-my-postgres-postgresql-0, data-my-postgres-postgresql-1, PVC stays even if Pod recreated
 4. Ordered Startup / Shutdown, StatefulSets start sequentially:, 0 → 1 → 2, Not parallel, Very important for DB clusters

Real Production Example, PostgreSQL primary-replica cluster:, postgres-0 → primary, postgres-1 → replica, postgres-2 → replica Each has: own disk, own hostname, stable identity
 IMPORTANT Experiment, Run: "kubectl get statefulset -n dev" You’ll see PostgreSQL StatefulSet, Inspect It, "kubectl describe statefulset my-postgres-postgresql -n dev"
 Observe:, replicas, volumeClaimTemplates, service name, MOST IMPORTANT SECTION Look for:, volumeClaimTemplates:, This is what auto-creates PVCs per replica.

KEY ARCHITECTURE UNDERSTANDING
 Deployment: Pods are replaceable
 StatefulSet: Each Pod has identity + storage
 VERY IMPORTANT INTERVIEW QUESTION, Why not use Deployment for PostgreSQL?, 
 Answer:, Deployment Pods are interchangeable and ephemeral, Databases need:, stable identity, stable storage, ordered startup, predictable networking, Hence StatefulSet.

cmd : "kubectl get statefulset my-postgres-postgresql -n dev -o yaml"

Conclusion : 
Whenever I scale my stateful set (ex : 2 replicas) then 2 postgres pods will get created and for the same 2 corresponding pvc will get created. 
Let us say pod 1 -> pvc 1 , pod 2 -> pvc 2 got created data of pvc 1 will be duplicated/replicated in pvc 2.
Imp to note that we have 2 postgres pods/pvc does not imply that both stores different data.
If we scale down replicas to 1 then 2ndly created pod/pvc will go down.
Data Persists After Pod Deletion, Even if Pod is deleted:, PVC survives, data survives, new Pod reattaches same storage. This is:, persistence
Always pod0/pvc0 will e considered as primary(This is from rostgres inbuilt platform chart) and if this goes down then pod1/pvc1 can be promoted as primary.
Replicas are application-level replication, NOT Kubernetes replication, This is extremely important, Kubernetes does NOT duplicate DB data automatically, Instead:, PostgreSQL itself replicates data
Ordered startup is CRITICAL in distributed systems, This is much deeper than “pods start in order”, Why?, Because replicas depend on primary availability, Example:, postgres-1 cannot replicate, until postgres-0 is available, That’s why:, startup ordering matters
Scaling StatefulSets is NOT same as scaling Deployments, Deployment scaling: more identical app instances. StatefulSet scaling: more distributed-system members
Pods are ephemeral(temporary / short-lived), but storage persists.

CI / CD for for kubernetes

Without CI/CD:
Developer-> Build JAR manually -> Build Docker manually -> Push Docker manually -> Run Helm manually -> Deploy manually.
Problems: Human mistakes,Slow deployments,No standard process,No audit trail.

CI/CD automates this : Git Push → Pipeline Starts → Build → Test → Package → Deploy.

What is CI? 
Focus on Code Quality 
Responsibilities : Compile code, Run tests, Build artifact, Build docker image.
Example : Java Code → mvn clean install → Unit Tests → Build Docker Image. and Output: Docker image

What is CD? CD = Continuous Delivery / Deployment
Focus: Deploying application
Responsibilities:Deploy Helm Chart -> Upgrade Kubernetes ->Rollback if needed
Output: Running Application

Typical Kubernetes CI/CD Flow
Developer → Git Commit → CI Pipeline → Build JAR → Run Tests → Build Docker Image → Push Image Registry → CD Pipeline → Deploy Helm Chart → Kubernetes.

What is Image Registry?
 After Docker image is built:
 "dock-test:v5" It must be stored somewhere that place is docker registry, 
 Examples: Docker Hub, Amazon Elastic Container Registry, Google Artifact Registry, Azure Container Registry.

What changes in Helm?
Suppose current image tag is v3, Pipeline builds v4, Pipeline updates image tag from v3 to v4, Then deploys.

What is the biggest production concept?, The developer does NOT deploy source code, The developer deploys Docker Images, Kubernetes never sees your Java code,
Kubernetes only sees Docker Images.

Real Example Using Your Project
Git Repo → Spring Boot Code -> You commit changes.
Pipeline does: : mvn clean package → dock-test.jar → docker build → dock-test:v4 → push registry.
Now CD begins: Update Helm values → image.tag=v4 → helm upgrade → Kubernetes.
Result: New Pods, Running v4.

Conclusion A production Kubernetes deployment usually follows:
Git → CI → Build JAR → Build Docker Image → Push Registry → CD → Helm Upgrade → Kubernetes.

Problems :Human mistakes, Different processes, No audit trail, Slow releases.

Jenkins automates this: Git Push → Jenkins → Build → Test → Docker Build → Deploy.

Jenkins Architecture
Old Terminology:
Jenkins Master 
      ↓
Jenkins Agent 

Current Terminology
Jenkins Controller
      ↓
Jenkins Agents

Developer → Git → Jenkins Controller → Triggers Job → Agent Executes Work.
Developer pushes code to Git, Jenkins Controller detects the change and triggers a job, and the Jenkins Agent executes the actual build work.

Ex :
Agent 1
   mvn clean package
Agent 2
   docker build
Agent 3
   helm upgrade

What is a Pipeline? - Series of automated steps
Example : Checkout Code → Build → Test → Build Docker Image → Push Docker Image → Deploy.

Jenkinsfile? - Pipeline as Code
Instead of configuring jobs manually through UI, we store pipeline definition in Git.
Conceptually :
Stage 1 :  Checkout
Stage 2 :  Build
Stage 3 :  Test
Stage 4 :  Docker Build
Stage 5 :  Deploy

Application Pipeline : 
Let's use your Spring Boot app 
Current manual process: Code Change → mvn clean package → docker build → docker push → helm upgrade.
Jenkins automates: Git Commit → Jenkins Trigger → Build JAR → Run Tests → Build Docker Image → Push Image → Deploy.

Real Production Example : Suppose you change:
@GetMapping("/version")

   return "v4";
}

Then: "git push"

Jenkins automatically: Pull code → Build JAR → Run tests → Build image → Push image → Deploy.  (No human intervention)

| Concept     | Meaning                          |
| ----------- | -------------------------------- |
| Job         | A unit of work                   |
| Pipeline    | Sequence of stages               |
| Stage       | Build/Test/Deploy step           |
| Jenkinsfile | Pipeline definition              |
| Controller  | Orchestrates jobs                |
| Agent       | Executes jobs                    |
| Trigger     | Starts pipeline                  |
| Workspace   | Folder where code is checked out |

Let's underwstand about jenkins UI :

When you login you'll see: 
1.Dashboard : This is the Jenkins home page. It displays your Jobs, Build History, and Nodes.
Think : Dashboard = Control Center

2. Job : A Job is a unit of work in Jenkins. Examples include building a Spring Boot application, deploying a Kubernetes application, or running tests. In modern Jenkins environments,
 the most commonly used type is a Pipeline Job.
 
3. Build : Every pipeline execution is called a Build. For example, Build #1, Build #2, and Build #3. 
This is similar to Helm revisions, where each execution gets a unique number and history is maintained for tracking and troubleshooting.
 
4. Build History : is a record of previous pipeline executions that Jenkins stores. For example, Build #1 may be successful, Build #2 may fail, and Build #3 may succeed. 
This history is extremely useful for troubleshooting, tracking changes, and identifying when issues were introduced.
 
5. Console Output : is the most important screen in Jenkins. It shows the detailed execution logs for every step, including Git clone operations, Maven builds, Docker builds, Helm commands,
and any errors encountered. Whenever a build fails, the first place to check is the Console Output, as it usually contains the exact cause of the failure.

6. A Workspace : is the folder where Jenkins downloads and works with your source code. For example, Jenkins clones your GitHub repository into the workspace and then runs commands 
such as `mvn clean package` from that location. You can think of the workspace as a temporary working directory used during pipeline execution.

7. Nodes :are the machines where Jenkins jobs execute. You can view them by navigating to **Manage Jenkins → Nodes**. 
You should see a **Built-In Node**, which is where your jobs currently run. Since you are learning Jenkins locally, the Controller and Agent are running on the same machine, 
so all job execution happens on the built-in node.

8. Credentials : allow Jenkins to securely store sensitive information such as Git passwords, Docker passwords, JFrog tokens, and kubeconfig files.
 In production environments, these values are never stored directly inside the Jenkinsfile. Instead, Jenkins manages them through its Credentials store. 
 Later, you will use Credentials for tasks such as Docker Hub authentication and GitHub access.

Before creating a pipeline, verify that Jenkins can execute commands correctly. Go to **Manage Jenkins → System Information** and look for **java.version**.
 You should see a valid Java version listed, which confirms that Java is available to Jenkins.

Our future pipeline will execute commands such as `mvn clean package`, `docker build`, `docker push`, and `helm upgrade`.
 A common question is whether the Jenkins container already includes Maven, Docker CLI, Helm, and kubectl. The answer is no.
 The default Jenkins image typically contains only Java and Jenkins itself. Additional tools such as Maven, Docker CLI, Helm, and kubectl must be installed or provided separately 
before Jenkins can use them in pipelines.

For learning purposes, we have two options. 

Option A :The recommended approach is to use Jenkins only to understand pipelines first. In this approach, you start with a simple pipeline that runs a Hello World example, 
performs a Git checkout, and then executes a Maven build. Once you are comfortable with pipeline concepts, we can move on to understanding Jenkins agents and more advanced setups.

Option B is to immediately configure Jenkins with all the tools required for a complete CI/CD pipeline, including Maven, Docker, Helm, and kubectl. 
This approach is closer to a real-world production setup because Jenkins can build, package, containerize, and deploy applications. However, it requires significantly 
more initial configuration and setup compared to starting with basic pipeline concepts.

My recommendation is to focus on understanding CI/CD rather than becoming a Jenkins administrator.
