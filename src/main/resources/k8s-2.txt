ConfigMap :
A ConfigMap is used to store external configuration for applications.
Instead of hardcoding values inside your Spring Boot app or Docker image, Kubernetes injects configuration dynamically.

Why ConfigMap Is Needed ?
 Without ConfigMap -> spring.datasource.url=jdbc:mysql://dev-db:3306/test -> is hardcoded inside app.
 problem : different values needed for dev/qa/prod, image rebuild required for every environment,not flexible
 ConfigMap solves this.
 
 What ConfigMap Stores -> environment variables,URLs,application properties,feature flags,ports,non-sensitive configs
 Examples : DB_HOST, DB_PORT,APP_ENV,LOG_LEVEL,API_URL
 
 Important Rule : ConfigMap is for NON-sensitive data.Do NOT store ->passwords,API secrets,tokens
Sensitive data goes into "Secret" which we will learn later

Approach 1 : 
---------------
configmap.yml
apiVersion: v1
kind: ConfigMap

metadata:
  name: dock-test-config
  namespace: dev

data:
  APP_ENV: dev
  APP_NAME: dock-test-app
  LOG_LEVEL: DEBUG
------------
Using ConfigMap In Deployment :
Now connect ConfigMap to container.

Update deployment.yml :
spec:
  containers:
    - name: dock-test-container
      image: vinayakwarad/dock-test

      env:
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: dock-test-config
              key: APP_ENV             
-----------			  
What Happens now -> Kubernetes injects -> APP_ENV=dev into container and Your Spring Boot app can read it.

Reading it in our springboot application :
@Value("${APP_ENV}")
private String env;

Approach 3 : File Mount Style

Instead of injecting individual environment variables, Kubernetes can mount an entire file from ConfigMap into the container filesystem.
Very common for:application.properties,application.yml,nginx.conf,logback.xml,custom configs
Without ConfigMap mounting: Your config file exists INSIDE Docker imag so changing config requires rebuilding image which is a problem.
With file mount style approach :  ConfigMap -> Mounted into container -> application.properties  (No image rebuild needed.)

Steps to follow to acheieve this approach :

Step 1 : configmap.yml
apiVersion: v1
kind: ConfigMap

metadata:
  name: dock-test-config
  namespace: dev

data:
  application.properties: |                     # Create a file named application.properties with multiline content
    server.port=8080
    app.message=Hello from Kubernetes


Step 2 : Apply ConfigMap
kubectl apply -f configmap.yml

Step 3 — Mount ConfigMap Into Pod -> Update deployment:
spec:
  containers:
    - name: dock-test-container
      image: vinayakwarad/dock-test

      volumeMounts:
        - name: config-volume
          mountPath: /config

  volumes:
    - name: config-volume
      configMap:
        name: springboot-config
		
# What ahppens now ? Kubernetes creates file: /config/application.properties inside container and Content comes from ConfigMap.		

****VIP**** Whenever you have changes in your config file it is recommended to "restart our deployment" after applying the config map - As most applications 
ead config only during startup and do not continuously watch files
Best practice in realtime projects run below commands- Safe and predictable:
"kubectl apply -f configmap.yml -n dev"
"kubectl rollout restart deployment dock-test-deployment -n dev"

Step 4 : Verification

Enter pod : kubectl exec -it <pod-name> -n dev -- sh
Check file: cd /config
               ls
               cat application.properties
You will see:
server.port=8080
app.message=Hello from Kubernetes

- How Springboot uses it? 
As environment variable :--
env:
  - name: SPRING_CONFIG_LOCATION
    value: /config/application.properties

LIVELINESS AND READLINESS :

Liveliness and readliness and Startup Probe (Third Important Probe): are critical for production-grade applications.

They help Kubernetes answer:
1. Is application alive?
2. Is application ready to serve traffic?
These are NOT the same thing.

Why Probes Are Needed

Suppose your Spring Boot app:
starts slowly
hangs internally
database connection breaks
deadlocks occur
Container may still be: RUNNING but application is unusable.

Kubernetes needs a way to detect this automatically.

Two Main Probes
Probe	Purpose
Liveness Probe	Is app alive?
Readiness Probe	Is app ready for traffic?

Note : Liveliness and readiness should be added in Deployment.yml file

1. Liveness Probe
Asks: Should Kubernetes restart this container? 
If liveness fails repeatedly: Kubernetes kills and restarts container

Example Real Problem
App gets: deadlocked,memory stuck, infinite loop, HTTP server stops responding then Liveness probe fails.Kubernetes auto-restarts pod.Very important self-healing feature.

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080

  initialDelaySeconds: 30
  periodSeconds: 10

| Field                 | Meaning                 |
| --------------------- | ----------------------- |
| `httpGet`             | Check HTTP endpoint     |
| `path`                | Endpoint to call        |
| `port`                | Container port          |
| `initialDelaySeconds` | Wait before first check |
| `periodSeconds`       | Check every X seconds   |

Liveness = FAIL
↓
Kubernetes restarts pod

2. Readiness Probe
Asks: Can this pod receive traffic right now? 
If readiness fails: pod removed from Service load balancing BUT container is NOT restarted.

Example Real Scenario
Spring Boot starts. But:DB connection not ready, Kafka not connected,Camunda engine still initializing. Readiness probe says: NOT READY.Kubernetes waits and Traffic is NOT sent yet.

| Situation       				| Liveness 					| Readiness |

| App hung     	  				| Restart pod 				| Remove traffic |
| App starting 	  				| Usually ignored initially | Block traffic |
| DB temporarily unavailable 	| Maybe no restart 			| Stop traffic |

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080

  initialDelaySeconds: 20
  periodSeconds: 5
  
  Real Runtime Behavior

Pod created
↓
Readiness = FAIL
↓
No traffic
↓
DB connected
↓
Readiness = SUCCESS
↓
Traffic starts

Spring Boot Best Practice : Use dependency :Spring Boot Actuator
It provides health endpoints:
/actuator/health
Updaate in apps.props :
management.endpoints.web.exposure.include=health
management.endpoint.health.probes.enabled=true


3. Startup Probe (Third Important Probe)
Useful for slow-starting apps.
Prevents liveness probe from killing app too early.
Very useful for: Camunda,large Spring Boot apps, JVM-heavy apps

Example Full Production Setup
startupProbe:
  httpGet:
    path: /actuator/health
    port: 8080

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
	
Extremely Important Production Concept
Without readiness probes:traffic may hit pod before app is ready
Without liveness probes:hung apps may never recover automatically
These probes are heavily used in real production Kubernetes clusters.	

Complete Deployment.yml file with all 3 probes

apiVersion: apps/v1
kind: Deployment

metadata:
  name: dock-test-k8s
  namespace: dev

spec:
  replicas: 2

  selector:
    matchLabels:
      app: dock-test-k8s

  template:

    metadata:
      labels:
        app: dock-test-k8s

    spec:

      containers:

        - name: dock-test-k8s

          image: vinayakwarad/dock-test:v1

          ports:
            - containerPort: 8080


          # -------------------------------------------------
          # STARTUP PROBE
          # -------------------------------------------------
          # Checks whether application has fully started.
          #
          # Useful for slow-starting applications like:
          # - Spring Boot
          # - Camunda
          # - JVM-heavy applications
          #
          # Until startup probe succeeds:
          # - liveness probe is disabled
          # - readiness probe is disabled
          #
          # Prevents Kubernetes from killing app too early.
          # -------------------------------------------------

          startupProbe:

            httpGet:
              path: /actuator/health
              port: 8080

            initialDelaySeconds: 10   # Wait before first probe
            periodSeconds: 5          # Probe every 5 seconds
            failureThreshold: 30      # Allow many failures during startup



          # -------------------------------------------------
          # READINESS PROBE
          # -------------------------------------------------
          # Checks whether app is ready to receive traffic.
          #
          # If readiness fails:
          # - pod removed from service load balancing
          # - NO restart happens
          #
          # Used for:
          # - DB connection readiness
          # - Kafka readiness
          # - app initialization
          # -------------------------------------------------

          readinessProbe:

            httpGet:
              path: /actuator/health/readiness
              port: 8080

            initialDelaySeconds: 20
            periodSeconds: 5
            failureThreshold: 3



          # -------------------------------------------------
          # LIVENESS PROBE
          # -------------------------------------------------
          # Checks whether application is alive.
          #
          # If liveness fails repeatedly:
          # Kubernetes restarts container automatically.
          #
          # Used for:
          # - deadlocks
          # - hung JVM
          # - frozen application
          # -------------------------------------------------

          livenessProbe:

            httpGet:
              path: /actuator/health/liveness
              port: 8080

            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 3
			
Real Production Importance
These probes are critical because they enable:
self-healing
zero-downtime deployments
safe rolling updates
traffic protection
automatic recovery

Resource Limits : (Deployment.yml)

Why Resource Limits Are Needed

Without limits:
one buggy app may consume all memory
CPU spikes may affect other apps
node can become unstable

Kubernetes is a shared environment.So resources must be controlled.

| Concept  | Meaning                      |
| -------- | ---------------------------- |
| Requests | Minimum guaranteed resources |
| Limits   | Maximum allowed resources    |

| Resource | Meaning          |
| -------- | ---------------- |
| CPU      | Processing power |
| Memory   | RAM              |

Note : Schedular is the one which decides where our pod needs to be created.

containers:
  - name: dock-test-k8s
    image: vinayakwarad/dock-test:v1
    ports:
      - containerPort: 8080

    resources:
      requests:
        memory: "256Mi"  #Min memory for our container that will be allocated at startup
        cpu: "250m"      #Min CPU for our container that will be allocated at startup
      limits:
        memory: "512Mi"  #Max memory for our container can get allocated to our container
        cpu: "500m"      #Max CPU for our container can get allocated to our container (500m = 0.5 core)
		
If container exceeds memory limit then it gets crashed with OOMKilled (Out of memory killed)		

How to checck metrics in Minnikube? Install metrics server: : "minikube addons enable metrics-server"
Verify Usage : "kubectl top pods"
NAME               CPU    MEMORY
dock-test-pod      20m    180Mi

Check Limits On Pod
kubectl describe pod <pod>

What Happens Without Requests/Limits?
Kubernetes uses:BestEffort QoS Risky in production.Pods may:consume excessive resourcesand get evicted first.

QoS Classes - Quality of Service (Very Important)
| QoS        | Condition          |
| ---------- | ------------------ |
| Guaranteed | requests == limits |
| Burstable  | requests < limits  |   (Most apps use Burstable)
| BestEffort | no requests/limits |

Recommended Spring Boot Starting Values For small Spring Boot apps:
requests:
  memory: "256Mi"
  cpu: "250m"
limits:
  memory: "512Mi"
  cpu: "500m"
  
Extremely Important Production Concept : This distinction is very important in interviews and real production Kubernetes.
Requests affect:scheduling
Limits affect:runtime enforcement
 
Note :
Kubernetes scheduler checks:Does node have enough FREE requested resources?before placing pod.
Scheduler uses:REQUESTS	& NOT limits. 
Limits matter AFTER pod starts. If pod limit was 700Mi and our pod consumer more memory than that then it will crash with OOMKilled
 
| Resource              | Behavior         |
| --------------------- | ---------------- |
| CPU limit exceeded    | throttled/slowed |
| Memory limit exceeded | container killed |

Requests = scheduling guarantee
Limits = runtime boundary

Horizontal Pod Autoscaler uses resource requests for scaling calculations.Without proper requests:autoscaling behaves badly

4.What is statefulset?
Problem it solves: Some applications need, stable identity, stable storage, ordered startup/shutdown,
 Examples:, databases, Kafka, Redis cluster, Elasticsearch, Zookeeper A normal Deployment cannot guarantee this properly.
 
| Feature             | Deployment | StatefulSet |
| ------------------- | ---------- | ----------- |
| Pod names stable?   | No         | Yes         |
| Persistent identity | No         | Yes         |
| Stable storage      | No         | Yes         |
| Ordered startup     | No         | Yes         |
| Best for            | APIs       | Databases   |

* Deployment Behavior, Pods get random names:, myapp-7f5d9, myapp-8h2ks, If Pod dies:, new Pod gets new name, storage may change, Fine for Spring Boot APIs.
* StatefulSet Behavior, Pods get fixed names:, mysql-0, mysql-1, mysql-2, If Pod restarts:, same name returns, same storage returns, VERY important for databases.
* Stable Pod Identity : Always predictable:, mysql-0, mysql-1, mysql-2, 
 Stable Persistent Volume : Each Pod gets dedicated storage, Example:, mysql-0 -> PVC-0, mysql-1 -> PVC-1, Storage survives Pod restart
3. Ordered Startup: Pods start sequentially: mysql-0 starts first, mysql-1 starts second, mysql-2 starts third, Important for clustered databases. 

* Basic StatefulSet Example
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql
  replicas: 2
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8
          ports:
            - containerPort: 3306
			
* StatefulSet usually needs: Headless Service. Example: clusterIP: None, Why?, Because each Pod gets unique DNS Example: mysql-0.mysql, mysql-1.mysql, This enables Pod-to-Pod communication.
* Storage in StatefulSet, Usually uses: volumeClaimTemplates. Kubernetes auto-creates PVC per Pod.
Ex :
volumeClaimTemplates:
  - metadata:
      name: mysql-data

    spec:
      accessModes: ["ReadWriteOnce"]

      resources:
        requests:
          storage: 1Gi
| Technology      | Uses StatefulSet? |
| --------------- | ----------------- |
| MySQL           | Yes               |
| PostgreSQL      | Yes               |
| Kafka           | Yes               |
| Redis cluster   | Yes               |
| Elasticsearch   | Yes               |
| Spring Boot API | Usually No        |

* Important Interview Understanding, StatefulSet ≠ “stateful application only”, It means:, application needing stable identity/storage/order

Conclusion : 
Stateful applications need stable Pod identities.

A normal ClusterIP Service load-balances requests to any available Pod,
which is unsuitable for Pod-to-Pod communication in distributed databases.

A Headless Service (clusterIP: None) provides stable DNS names for each Pod,
allowing replicas to communicate with specific Pods such as the primary.

Stateless applications usually use normal ClusterIP Services because any Pod can handle the request.

1. Why replicas cannot use a normal ClusterIP Service

ClusterIP resolves to random pods, so postgres replicas cannot reliably find the primary pod to replicate data from primary and maintain data consistency.

Example:

postgres-1
    ↓
postgres-service
    ↓
could go to postgres-0 (primary)
or postgres-2 (replica)
or postgres-1 itself

For replication, PostgreSQL needs: postgres-1 → connect specifically to postgres-0 : not "any available pod".

That's why stable DNS names are needed:

postgres-0.my-postgres-headless
postgres-1.my-postgres-headlessYour understanding:

ClusterIP resolves to random pods, so postgres replicas cannot reliably find the primary and data consistency will be lost.

- Service does NOT directly point to Pods.
Instead: Service-> Label Selector -> Matching Pods 

service.yml :
spec:
  selector:
    app: dock-test-k8s  #Finds matching pods using labels and Routes traffic to them
	
The Service becomes a stable entry point while Pods can be created and destroyed behind it.

Typical responsibilities: Chart name, Chart version, Application version, Dependencies, Description.
Dependencies :

What does dependency mean in Helm? One Helm Chart requires another Helm Chart.
Instead of asking users to install PostgreSQL separately, your chart can declare.
